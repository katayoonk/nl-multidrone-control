Operator language interface with typed MCP tools and a deterministic safety gate over ROS/PX4

Abstract

This project explores a practical way to operate multiple drones through natural-language instructions while keeping flight execution deterministic, constrained, and auditable. An operator interacts through either a lightweight Python chat interface or Claude Desktop. The language model interprets the request and selects a typed drone capability exposed through the Model Context Protocol (MCP). Before any command reaches a vehicle, a deterministic safety gate checks the current drone state and the requested action. Approved commands are forwarded to the existing ROS and flight-control stack; rejected commands return a clear reason to the operator. The model therefore proposes what should happen, while established drone software remains responsible for how the vehicle flies.

Method

The system inserts a thin language and tool layer above an existing multi-drone stack. The language model never generates motor commands or flight setpoints. It selects a capability and supplies structured arguments; deterministic code validates and executes the request.

Interface capabilities

  • State. Read drone state and telemetry.
  • Flight. Takeoff, landing, and return-to-launch.
  • Motion. Relative movement forward, backward, left, right, up, and down by a requested distance; yaw by a requested angle.
  • Camera. Gimbal pitch/yaw control, image capture, and continuous capture.
  • Coordination. Point one drone toward another using relative positions (look_at).
  • Missions. Start, monitor, and stop existing behavior-tree missions.

Safety gate

The gate checks conditions such as whether the drone is known and connected, whether it is airborne when motion is requested, allowed movement and altitude ranges, battery state, gimbal limits, and the configured operating fence. Every request, gate decision, and result is logged.

Real-world experiment

The first experiment tested the complete system with two physical drones. Commands were issued through the custom Python chat interface and through Claude Desktop using the same MCP tool server. The demonstration covered takeoff and landing, directional and vertical motion with specified distances, camera pitch and yaw control, image capture, return-to-launch, and a coordinated command in which one drone oriented itself and its camera toward the other drone.

The experiment demonstrated that natural-language requests can be translated into structured, executable drone actions without allowing the language model to directly generate low-level flight commands. It also exercised the safety path: commands that did not match the reported vehicle state could be rejected before reaching the flight stack.

Contributions

  • Reusable skill layer over existing ROS/PX4 drone interfaces.
  • Deterministic, configurable safety gate and JSONL audit log.
  • ROS service exposing gated skills through a single agent endpoint.
  • Host-side MCP server with typed schemas for each supported capability.
  • Python chat interface plus Claude Desktop / Claude Code integration.
  • Telemetry, camera capture, gimbal control, inter-drone look_at, and behavior-tree tools.
  • Reproducible agent container with rosbridge and required dependencies.
  • Validation in simulation and with a two-drone real-world experiment.
  • Token, prompt, and end-of-day agent-loop inspection tools for performance analysis.

Current status

The end-to-end architecture is operational in simulation and has been demonstrated on two real drones. The current phase is focused on systematic evaluation, efficiency, and additional safety and verification mechanisms.
